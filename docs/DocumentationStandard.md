# 仓库注释与文档标准（对齐 daemon_supervisor）

> 目标：让“第一次接触代码的人”只看文档和文件头注释，就能回答：
> 1) 这个模块负责什么？不负责什么？
> 2) 生命周期/线程模型是什么？
> 3) 关键数据流（Topic / CAN / UART）从哪来、到哪去？
> 4) 故障与守护策略是什么？

## 1. 文件头注释规范（.h/.hpp/.c/.cpp）

每个**对外接口头文件**、**任务入口**、**核心类实现文件**，应包含如下结构的文件头注释（Doxygen 风格，便于后续生成文档）：

- `@file`：文件名
- `@brief`：一句话概括职责
- “核心逻辑/设计思路”：
  - 该文件提供的能力与边界
  - 关键状态机/时序（必要时给 ASCII 图）
  - 线程/中断上下文约束（是否可在 IRQ 调用，是否需要临界区）
  - 数据源与数据汇（Topic 名称、CAN ID、UART 端口等）
- “常见误用/注意事项”：例如
  - 禁止直接调用 BSP 发送，必须发布到 Topic，由 TxTask 统一发送
  - 必须在收到新数据时 feed 守护，不要用空转周期 feed

建议文件头结构：

```cpp
/**
 * @file xxx.cpp
 * @brief 一句话说明
 *
 * 设计思路：
 * =========
 * - ...
 *
 * 线程模型：
 * =========
 * - ...
 *
 * 数据流：
 * =======
 * - In: ...
 * - Out: ...
 *
 * 注意事项：
 * =========
 * - ...
 */
```

## 2. 模块文档规范（每个一级目录一个 *.md）

每个模块目录（例如 `Interaction/`、`Device/`、`Communication/`）放置一个 `模块名.md`，结构如下：

- 概述：模块职责与边界
- 目录/文件结构：列出关键文件（不必全量）
- 生命周期：初始化、启动顺序、RTOS 任务
- 数据流：Topic / CAN / UART / 共享内存
- 守护/容错：daemon_supervisor 的 client 注册与 feed 判据
- 开发约束：例如禁止动态内存、禁止异常/RTTI（如适用）

## 3. 注释密度与“不要写废话”

- **解释“为什么”多于“是什么”**：代码本身已经说明了“做什么”，注释应解释取舍和约束。
- 不要逐行翻译代码。
- 任何“非显然”的常量、阈值、ID、周期，都需要写来源或理由。

## 4. 范围约束

- 不修改 `ThirdParty/` 的第三方库源码（除非专门要求）。
- 不在注释中承诺代码并不存在的行为；文档必须来自真实实现。
